## 2. The revised read rule (adopted verbatim)

> No unbounded member × fixture fan-out in the cron invocation. Bounded authoritative reads inside
> capped Queue jobs are allowed and required for the pre-send privacy/correctness check.

This is a better rule than the one in the frozen spec, because it puts the authoritative check where
correctness actually needs it — immediately before the send — instead of trying to make a cached
snapshot trustworthy. The whole of §3 follows from it.

## 3. How each blocker changes the design

### 3.1 Fan-out withdrawn — Queues adopted (blocker 2)

Sol's 32-invocation limit is confirmed verbatim in Cloudflare's Service Bindings documentation:
*"A single request has a maximum of 32 Worker invocations, and each call to a Service binding counts
towards this limit. Subsequent calls will throw an exception."* The v1 design needed ~75 children.
It could not have run. Withdrawn.

There is a second, independent reason Queues is right, and it survives the plan finding: **the
6-simultaneous-outgoing-connection limit is identical on Free and Paid.** No single invocation can
push thousands of APNs requests quickly however large its subrequest ceiling, because it can only hold
six connections open. Queue consumer concurrency (up to 250, push-based) is the mechanism that actually
parallelises delivery. Sol's architecture is correct for a better reason than the one it was given.

### 3.2 The KV marker withdrawn — SQLite DO ledger (blocker 3)

Sol's three objections to `notified:fx:<fixtureId>` are all correct: KV is eventually consistent, the
read-modify-write loses concurrent updates, and a crash between APNs success and the marker write opens
a duplicate window. A KV value cannot express a claim.

A SQLite-backed Durable Object can, because it is single-threaded and transactional:

```sql
CREATE TABLE IF NOT EXISTS delivery (
  uid        TEXT NOT NULL,
  fixture_id TEXT NOT NULL,
  league     TEXT NOT NULL,
  state      TEXT NOT NULL,          -- 'claimed' | 'sent' | 'failed'
  claimed_at INTEGER NOT NULL,
  sent_at    INTEGER,
  kickoff_at INTEGER NOT NULL,
  PRIMARY KEY (uid, fixture_id)
);
```

`claim()` is one `INSERT … ON CONFLICT DO NOTHING` returning only newly-inserted rows. Two consumers
racing the same uid/fixture: one gets the row, the other gets an empty set and sends nothing. No lost
updates, by construction rather than by analysis.

**The crash window is unavoidable and is documented, not hidden.** A consumer that dies after APNs
accepts a push but before `recordSuccess()` leaves a `claimed` row; when the Queue redelivers, that row
is re-claimable after the visibility timeout, and the user can receive a second push. The mitigation is
Sol's: a stable `apns-collapse-id` per user+fixture means Apple *replaces* the earlier notification
rather than stacking it, so the lock screen shows one entry. The contract is therefore honest
at-least-once-with-collapse, never at-most-once. Fail-closed is chosen deliberately: if the DO is
unreachable the consumer throws and nothing sends, because silence is a better failure than duplicates.

### 3.3 The push index deleted (blocker 4)

Sol's fourth blocker identifies a real hole and the right answer is to remove the cache rather than
defend it. Sol's dilemma was exact: uids-only recreates per-user fan-out; tokens-and-mutes makes the
cache an authority that key-name reconciliation cannot validate — reconciliation detects a *missing*
uid but never a *stale token* or a *stale mute*, which is precisely the privacy-bearing case.

**In v2 there is no push index.** Tokens, mutes and membership are read authoritatively from
`push:<uid>` and `member:<code>:<uid>` inside the capped Queue job, immediately before sending, which
the revised read rule requires. There are no concurrently-written shards, so there is no lost-update
analysis to write.

One index survives, in a shape that cannot lose updates:

**`slatefx:<fixtureId>:<leagueCode>` → `{ "period": "<period>" }`**

One key per (fixture, league) pair, written only by that league's own publish/amend path — a **single
writer per key**, so concurrent publishes touch disjoint keys and never contend. Discovery is
`KV.list({prefix:"slatefx:<fixtureId>:"})`, which returns league codes **in the key names** with zero
value reads. Its contents are league codes and a period: **no user data, no tokens, no mutes.**

It is explicitly a **discovery hint, not an authority**. The consumer re-reads the real published slate
before sending, so a stale entry costs a wasted job and never a wrong send.

## 4. The design

### 4.1 Cron (every 15 min) — plans, never sends

1. Load fixtures (module cache; ≤2 external fetch).
2. Due fixtures = kick-off inside the 60-minute reminder window and not yet started. **Window preserved.**
3. Acquire a planner lease from the DO (`plan:<fixtureId>`, TTL 90 min) — one planner per fixture.
4. Per due fixture: `KV.list({prefix:"slatefx:<fixtureId>:"})` → league codes, key names only.
5. Membership: `KV.list` over the due leagues' `member:<code>:` prefixes — key names only, zero value
   reads, bounded by the due-league count.
6. Build (uid, fixtureId, leagueCode) triples. League = **lexicographically smallest** eligible code
   for that uid, from the sorted key names — the D2 stable server-side order, unchanged and still free.
7. Chunk into jobs of **≤45 triples over ≤3 distinct fixtures and ≤3 distinct leagues**, and
   `sendBatch` them to the queue.
8. A single **sweep** pass at the last tick before kick-off asks the DO which uids are still unsent for
   that fixture and enqueues only those. Two planning passes per fixture, not four.

No token reads, no mute reads, no pick reads, no slate value reads in the cron. Nothing that can send.

### 4.2 Queue configuration

`max_batch_size = 1`, job ≤ 45 triples → **a consumer batch can never exceed 45 APNs requests**
(Sol's item 2), against a Free external-subrequest cap of 50 and a Paid cap of 10,000. Message size
≈ 2.7 KB, far under the 128 KB maximum and under the 64 KB billing unit, so one job is one operation.

### 4.3 Consumer — the authoritative pre-send check

1. `claim()` the triples in the DO → only the newly-claimed subset proceeds.
2. Bounded authoritative reads for that subset only:
   - `push:<uid>` — token and mute (**≤45 reads**)
   - `member:<code>:<uid>` — still a member (**≤45 reads**)
   - `picks:<fixtureId>` — no saved pick (**≤3 reads**, one per distinct fixture)
   - `custom_slate:<code>:<period>` — still in a published slate (**≤3 reads**)
3. Drop anything ineligible, and anything now past kick-off.
4. Send with `apns-expiration` = kick-off epoch seconds and a stable `apns-collapse-id` per user+fixture.
5. `recordSuccess()` on 2xx; `release()` on permanent failure so a retry can re-claim; throw on
   transient failure so the Queue redelivers. 410 Unregistered deletes `push:<uid>`.

Payload and lock-screen copy are unchanged from v1: `po: { v, f, l }` carried privately, alert text
says **"Your league"**, never a user-created name. Old clients ignore `po` (X1, N4).

### 5.1 The one place the Free envelope does not close

Queue, DO and KV-write budgets all hold comfortably at both scales. **KV reads do not, at 1,000.**

The notification path alone adds ~22,600 reads/day, and the *existing* app already runs 70,000–577,000
reads/day. Against a Free cap of 100,000/day the notification feature has no room at 1,000 recipients —
and neither does the app that is live today. On the verified Paid plan, KV reads are unlimited and this
is a non-issue.

I am reporting this rather than tuning the assumption to make the table close. If Sol wants the
notification path itself inside a 100,000-read/day envelope regardless, the lever is a per-consumer
membership check folded into the `push:<uid>` record, which halves consumer reads to ~11,300/day — at
the cost of reintroducing exactly the cached-authority problem blocker 4 correctly rejected. I do not
recommend it.

## 6. Capacity limit and spill (Sol item 7)

**10,000 recipients is formally unsupported**, as instructed. The exact binding constraints, in the
order they bite:

| Constraint | Sends/day it supports | Equivalent recipients @ 10 sends/day |
|---|---:|---:|
| KV reads 100,000/day (Free) | ~46,900 | **~4,690** |
| DO rows written 100,000/day | 50,000 | ~5,000 |
| Queue 10,000 ops/day | ~150,000 | ~15,000 |

**The Free-envelope capacity limit is ~4,700 recipients**, set by KV reads in the consumer's
authoritative check — and effectively lower once the live app's existing read load is counted against
the same budget. On the verified Paid plan, no quota binds; the practical limit becomes queue
throughput and the 6-connection ceiling, both far beyond any scale this app will see.

**Spill behaviour when a quota is exhausted:** the failing operation throws, the consumer does not ack,
and the Queue redelivers within its 24-hour retention. Reminders spill forward **only while still
pre-kick-off** — the consumer drops any triple whose fixture has started, and `apns-expiration` makes
Apple discard anything that outlives the kick-off even if a send is already in flight. Expired
reminders are logged with fixture, league and count, and are not retried.

**Picks, results and settlement are unaffected.** They share no queue, no DO and no code path with
delivery; a fully exhausted notification budget degrades reminders to silence and touches nothing else.

## 7. Traces

| Scenario | Behaviour |
|---|---|
| **Concurrency** — two consumers claim the same uid/fixture | `INSERT … ON CONFLICT DO NOTHING` inside the single-threaded DO. One claims, the other receives an empty set and sends nothing. |
| **Retry** — job partly failed | Queue redelivers the whole message; `claim()` returns only rows not already `sent`, so successes are never re-sent and only failures retry. This is the contract v1's KV marker could not prove. |
| **Crash between send and record** | Unavoidable. Row stays `claimed`; redelivery may re-send. `apns-collapse-id` per user+fixture makes Apple replace rather than stack, so the lock screen shows one notification. At-least-once with collapse, stated not hidden. |
| **Overlapping cron** | DO planner lease per fixture; the second run finds the lease held and plans nothing. Even without the lease, `claim()` would dedupe at send time. |
| **Stale index** — fixture amended out after publish | Consumer re-reads the authoritative published slate, finds it absent, drops the triple. Wasted job, no wrong send. A *missing* index key cannot occur from contention: one writer per key. |
| **Queue unavailable** | `sendBatch` throws in the cron, is caught and logged; nothing enqueued, nothing sent. The next tick retries while the fixture is still in window. Degrades to silence. |
| **DO unavailable** | `claim()` throws; consumer does not ack; Queue redelivers. Fail-closed by choice — no claim, no send. Degrades to silence, never to duplicates. |
| **User in 3 overlapping leagues with the same fixture** | Cron emits one triple, league = lexicographically smallest code. DO primary key `(uid, fixture_id)` makes a second triple unclaimable. Exactly one notification (N1). |
| **Pick saved between plan and send** | Consumer's authoritative `picks:<fixtureId>` read excludes them before any APNs call (N2). |
