## 1. The defect this has to design around

`notifyKickoffs()` (`worker/src/worker.js:1501`) currently:

- lists `push:` and reads **one KV value per registered device** — `O(R)` reads per tick;
- sends to **every** unmuted device for **every** pending fixture, with no membership, no slate and no pick check;
- records a single global marker `notified:<fixtureId>` — so a partial delivery either re-notifies everyone or nobody, and the payload carries no fixture or league, which is why taps land on Next.

Three separate `O(R)` or `O(R×F)` hazards. The plan below removes all three.

## 2. What the current key space already gives us for free

Two existing shapes do most of the work, and neither is changing:

| Existing record | Why it is decisive |
|---|---|
| `picks:<fixtureId>` → `{ uid: {p1,p2,ts} }` | Every user's pick state for one fixture lives in **one value**. "No saved pick" costs **1 read per fixture**, not per recipient-fixture. |
| `member:<code>:<uid>` | The uid is **in the key name**. `KV.list({prefix:"member:"})` returns the entire membership graph from key names with **zero value reads**. |

So membership and pick state are already free of fan-out. Only two things are not: the device tokens (`push:<uid>`, one value each) and "which leagues published this fixture" (`custom_slate:<code>:<period>`, one value per league per period). Those two get indexes — the same pattern the codebase already uses for `index:custom_mix` (`worker/src/worker.js:172`).

## 3. Record design

### 3.1 `index:push:<0..15>` — push registry projection *(new)*

Sixteen fixed shards, `shard = fnv1a(uid) % 16`. Value:

```json
{ "prem_1a2b…": { "t": "<64-hex APNs token>", "m": ["ELC"] } }
```

`m` omitted when empty. Written alongside `push:<uid>` on every existing write path — `savePushToken`, `setNotificationPrefs`, the APNs 410 delete, and account deletion (`worker.js:874`). `push:<uid>` **stays the authority**; the index is a derived cache.

- **Read cost: 16 per tick, constant in R.**
- Entry ≈ 121 bytes (uid is `prem_<uuid>` = 41 chars). At 10,000 recipients: ~76 KB per shard.
- 25 MB value ceiling ÷ 121 B × 16 shards = **~3.3 M recipients** before the shape itself breaks.

**Drift healing.** A shard upsert is read-modify-write, so two registrations landing in the same shard in the same millisecond could lose one. The cron therefore runs a reconciliation pass: `KV.list({prefix:"push:"})` (key names only, zero value reads) minus the union of index uids; any uid present in KV but missing from the index is healed with a single `push:<uid>` read. Steady state is 0; the pass is budgeted at ≤5 and capped, with the remainder healed on the next tick. This makes the index self-correcting rather than trusted.

### 3.2 `index:slate_fx:<fixtureId>` — published-slate reverse index *(new)*

```json
["ABCD", "WXYZ"]
```

League codes whose **published** slate currently contains this fixture, **sorted on write**. Written from the existing publish / amend / auto-publish / unpublish paths, which already compute added/removed deltas (`worker.js:744`), and from league deletion (`worker.js:922`).

Keyed by **fixture ID, not by date** — deliberately. A postponement changes a fixture's kick-off without touching any slate, so a date-bucketed index would go stale silently. Fixture ID is immune to rescheduling.

- **Read cost: 1 per pending fixture (F), zero per league.**
- Sorted on write means "lexicographically smallest eligible league code" (D2) is a head-of-list scan after intersecting with the user's codes — **in memory, zero reads**.

### 3.3 `notified:fx:<fixtureId>` — per-user success marker *(replaces `notified:<fixtureId>`)*

```json
{ "v": 1, "d": ["prem_1a2b…", "prem_3c4d…"] }
```

The uids with a **confirmed successful** APNs delivery. TTL unchanged (`NOTIFIED_TTL_S`, 2 days).

This is per-user/per-fixture *semantics* at **1 read + 1 write per fixture**. A retry on the next tick subtracts `d` from the eligible set: successes are never re-notified, failures are retried — which is exactly N6, and it is what the current global marker cannot do.

- 44 B per uid → 440 KB at 10,000. 25 MB ÷ 44 B = **~568,000 uids per fixture** of headroom.
- **Single writer.** Only the parent cron invocation writes this key, so there is no read-modify-write race between delivery workers (see §4).

### 3.4 Payload (D2)

```json
{ "aps": { "alert": { … }, "sound": "default" },
  "po": { "v": 1, "f": "<fixtureId>", "l": "<league code>" } }
```

`po` is private routing data, never rendered. Lock-screen copy says **"Your league"** — user-created names are never exposed. `l` is the lexicographically smallest league code eligible **for that user** for that fixture, resolved in memory. Old clients ignore `po` and behave exactly as today (X1, N4).

## 4. Per-tick algorithm and the delivery ceiling

The 1,000-subrequest ceiling counts **KV operations *and* `fetch`** — which means APNs sends count too. At 10,000 recipients the *reads* are trivial but the *sends* are the binding constraint, and it is worth saying plainly: no arrangement of KV can fix that, because 10,000 recipients × ~6 pending fixtures is ~60,000 APNs POSTs and one invocation is capped at 1,000 subrequests total.

**Resolution: bounded fan-out over a self Service Binding.** The parent cron invocation does all eligibility resolution (bounded reads, below), then dispatches slices of ≤800 sends each to `env.SELF` — a Service Binding to this same worker, one line in `wrangler.toml`. Each dispatched invocation is a separate Worker invocation with **its own fresh 1,000-subrequest budget**: ≤800 APNs fetches, **zero KV**, returning the list of uids it delivered to. The parent unions the results and writes the F markers itself. That keeps the marker single-writer, keeps every slice idempotent, and makes a slice failure cost nothing but a retry next tick.

Raising cron frequency alone was considered and rejected: `*/5` gives 12 ticks in the 60-minute window × ~900 sends = ~10,800, which does not clear 60,000. It is retained only as the degraded fallback if the Service Binding is unavailable.

### Parent tick, step by step

| # | Step | Subrequests |
|---|---|---|
| 1 | Fixture feeds (`allFixtures`, 60 s module cache) | 2 fetch on miss |
| 2 | `index:slate_fx:<id>` per pending fixture | F |
| 3 | `index:push:<0..15>` | 16 |
| 4 | `KV.list({prefix:"member:"})` — key names only | ⌈M/1000⌉ |
| 5 | `KV.list({prefix:"push:"})` — reconciliation, key names only | ⌈R/1000⌉ |
| 6 | Drift heal `push:<uid>` reads | ≤5 (0 steady state) |
| 7 | `picks:<fixtureId>` per pending fixture | F |
| 8 | `notified:fx:<fixtureId>` read per pending fixture | F |
| 9 | Dispatch to `SELF`, ≤800 sends per slice | ⌈E/800⌉ |
| 10 | `notified:fx:<fixtureId>` write per pending fixture | F |

Steps 1–8 are followed by eligibility evaluation that is **entirely in memory**: current member (step 4) ∧ fixture in a published current slate (step 2) ∧ no saved pick (step 7) ∧ competition not muted (step 3) ∧ not removed (absent from 3/4) ∧ not already delivered (step 8). D2's re-check immediately before APNs is the slice re-testing the pick map and marker snapshot it was handed, so a pick saved between scheduling and send is suppressed (N2).

### Where the ceiling actually bites

Marginal parent cost per recipient = 1/1000 (member page) + 1/1000 (push page) + k/800 (dispatch) ≈ **0.0095 subrequests**. Solving against the ceiling:

| R | member pages | push pages | dispatch | total |
|---:|---:|---:|---:|---:|
| 10,000 | 15 | 10 | 75 | 163 |
| 50,000 | 75 | 50 | 375 | 563 |
| **90,000** | 135 | 90 | 675 | **958** |

The design holds to roughly **90,000 recipients — 9× the 10,000 design point** — with no change. Past that, the next lever is a two-level dispatch tree (parent fans out to 16 shard-children, each of which dispatches its own slices with a fresh budget), which removes the dispatch term from the parent entirely; it is not needed now and is not being built now.

## 6. The N5 claim, explicitly

D2's read rule is "no per-member/per-fixture KV-read fan-out; in-memory eligibility evaluation over bounded/indexed records is allowed."

| Fan-out class | Reads in this design |
|---|---|
| per recipient | **0** — 16 constant index shards; `push:` list is key names only; heal is drift-bounded and normally 0 |
| per recipient × fixture | **0** — pick state is F reads, marker state is F reads |
| per member | **0** — membership comes from `member:` key names |
| per league | **0** — slate membership comes from F fixture-keyed index reads |

Every per-recipient and per-recipient-fixture term is zero. The only terms that grow with scale are `KV.list` **page** counts (key names, no values) and the dispatch count, which tracks sends rather than reads.

N5 will be asserted, not asserted-by-eye: the test harness counts every `KV.get` / `KV.put` / `KV.list` / `sendPush` call at each of the three scales and fails if any total exceeds the figures in §5 or if any per-recipient read appears.

## 7. Non-KV limits checked

- **CPU (30 s cron limit):** eligibility is set intersection over ~15,000 membership entries, ~10,000 index entries and 10 pick maps — sub-100 ms. Well clear, and it is the reason the work belongs in memory rather than in KV.
- **KV value ceiling (25 MB):** largest values are a push shard at ~76 KB and a fixture marker at ~440 KB at the 10,000 scale. Headroom quoted in §3.
- **KV write rate (1/s per key):** each marker key is written once per fixture per tick, ticks are 15 minutes apart, single writer. No contention.
- **KV list consistency:** `KV.list` is eventually consistent (already noted at `worker.js:1346`). A membership written seconds before a tick may be missed by that tick and picked up by the next — inside the 60-minute window this costs nothing, and the marker makes the later send correct rather than duplicate.
