## 1. Scorecard speed

### 1.1 Measured baseline

What opening a scorecard does today (`openMatchdayScreen` → `loadScorecardScreen`), strictly in order:

1. `loadFixturesForLeagues()` — only fetches a competition's fixture list not
   already loaded (cold tap / second competition). PL `/fixtures` 191 KB, ELC
   273 KB.
2. `/state?code&period&uid` for **every** league that played that day, in
   parallel. The network answer is always awaited; the device copy
   (`cachedRoundState`, already persisted) is used **only if the fetch fails**.
3. `ensureResultsRounds()` — a **second, sequential** batch of `/state` for any
   other league's week the "week complete" banner needs.
4. Only then `render()`.

Production measurements (Mac on home broadband, so 4G will be slower):

| Step | Measured |
|---|---|
| `/health` (zero server work), fresh connection | 0.33 s total: connect 21 ms, TLS +52 ms, first byte 314 ms |
| `/health` on a reused connection | 56 ms (the bare round trip to Cloudflare) |
| `/state` round, fresh connection (25 samples, 4 leagues) | 0.18–0.72 s, typically 0.2–0.4 s |
| `/state` round, reused connection | 117–271 ms |
| `/state` round, server-side (from logs, 15 samples) | wall 66–207 ms (median ~80 ms), **CPU 3–10 ms**: almost all of it is waiting on sequential KV reads |
| `/fixtures?competition=ELC&wx=1` (only on a cold tap) | 0.42 s, 273 KB |
| `scorecardModel` on the device (13 members, 2 matches) | median 0.12 ms: building the screen is free |

**Time to content today**
- **Typical open, fixtures already loaded:** one or two `/state` round trips.
  - Broadband: about 0.25–0.9 s.
  - 4G: estimated at about 0.5–1.5 s, adding about 100–200 ms per round trip and a slower TLS setup.
- **Cold tap needing a second competition's fixtures:** add about 0.4 s on broadband, more on 4G.
- **Second open:** no faster. Step 2 refetches even a settled round it already holds.

So Adam's "noticeable moment" comes from network round trips, run one after another, on every open. Device and server CPU are negligible.

Not yet measured: on-device timing in the real WKWebView over 4G. Build 38 adds a timing mark (see 1.6) so the next TestFlight run reports real numbers.

### 1.2 Device cache: render settled days instantly

- **What's immutable:** a day is immutable once every fixture of that league on that day is settled, i.e. `scorecardLinks` already lists it as done.
- **What to cache:** the scorecard *model input*, which is the round (`/state` for league+period) plus that day's fixture ids and scores. Store it in a new `STORAGE.scorecards` keyed `<code>:<ukDate>`, with `{ round, fixtures, settledAt, fullySettled }`. Bounded to this season's leagues the device still belongs to, and pruned like `roundStates`.
- **Open path:**
  1. Cache hit with `fullySettled`: render synchronously from cache, with no network. Target under 100 ms to visible content; it's really one frame.
  2. Cache hit without `fullySettled`, or a hit older than the round's `complete` flag: render the cache, then refresh silently. Re-render only if something changed.
  3. Miss: as today, with the changes in 1.3 and 1.4.
- **Correction safety:** a correction to a result after settlement changes the server round's `updatedAt` or a results revision. Every later `/state` for that league (League tab, My Picks) compares it and drops affected cache entries. No extra request.

### 1.3 Prefetch from My Picks

- When My Picks paints settled rows (`scorecardLinks` has done days), fetch the round for each league+day in the background once per session (Set `prefetched:<code>:<ukDate>`). That fills the cache from 1.2, using `requestIdleCallback` (or `setTimeout` 1 s), never blocking the paint.
- Most of the time the round is already in memory from My Picks or League. Then it's just a copy into the scorecard cache, with zero requests.
- Not on the web? Same code. The web gets it too.

### 1.4 Remove the sequential wait

- Render as soon as the **chosen** league's round is in. Other leagues' chips and the week-complete banner fill in when they arrive (`ensureResultsRounds` no longer gates `status = "ready"`).
- Don't refetch fixtures for a competition the day doesn't involve. `loadFixturesForLeagues` is scoped to the leagues in `scorecardLeagues(d)`.

### 1.5 Server cache of settled rounds

- **Where:** in `state()` for a round request (`period` given). When the computed round is `complete`, store the computed payload in KV `roundcache:<code>:<period>` with a results revision stamp. Later requests read that one key instead of the members, picks, slate and results reads. That's about 80 ms of KV waits down to one read, about 10–20 ms.
- **Privacy is unchanged:**
  - The viewer check (current member, `since` rules) still runs per request before anything is returned. The cache is the league's computed round, never a per-viewer answer.
  - Responses stay `private, no-store`, with no browser caching.
  - The Cache API isn't used, because it caches per colo by URL, which would key on `uid` and risk serving one viewer's response to another. KV holds only the round.
- **Invalidation** happens only where a settled round can change:
  1. a result correction (the results overlay POST and the settlement write when a settled fixture's score changes): delete `roundcache:<code>:<period>` for every league whose slate holds that fixture, found with the existing `slatefx:<fixture>:<code>` index;
  2. a member leaving or being removed (the table drops them): delete that league's `roundcache:*`;
  3. a nickname change: same as 2, or exclude nicks from the cache and join them at read time (preferred, since it's cheaper and never stale).
- **Safety net:** a 7-day TTL on the KV entry.
- **Tests:**
  - A cache hit returns byte-identical JSON to a cold compute.
  - A correction invalidates.
  - A non-member gets the same refusal as today.
  - A league with nicks changed shows the new nick.
  - No Cache API use.
