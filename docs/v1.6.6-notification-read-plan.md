## 2. The architecture

Unchanged from v2, where three of Sol's four blockers were upheld and applied.

**Fan-out is withdrawn.** Cloudflare's documented limit — *"A single request has a maximum of 32 Worker invocations, and each call to a Service binding counts towards this limit"* — killed it; v1 needed ~75 children. A second reason survives the plan question entirely: **the 6-simultaneous-connection limit is identical on Free and Paid**, so no single invocation can push thousands of notifications however large its subrequest ceiling. Queue consumer concurrency is what parallelises delivery.

**The KV marker is withdrawn.** KV is eventually consistent, its read-modify-write loses concurrent updates, and a crash between APNs success and the marker write opens a duplicate window. A KV value cannot express a claim. A SQLite Durable Object can:

```sql
CREATE TABLE IF NOT EXISTS delivery (
  uid TEXT NOT NULL, fixture_id TEXT NOT NULL, league TEXT NOT NULL,
  state TEXT NOT NULL,                       -- 'claimed' | 'sent' | 'failed'
  claimed_at INTEGER NOT NULL, sent_at INTEGER, kickoff_at INTEGER NOT NULL,
  PRIMARY KEY (uid, fixture_id)
);
```

`claim()` is one `INSERT … ON CONFLICT DO NOTHING` returning only newly-inserted rows, inside a single-threaded object. Two consumers racing the same uid/fixture: one claims, the other sends nothing. No lost updates by construction.

**The push index is deleted.** Sol's dilemma was exact — uids-only recreates per-user fan-out; tokens-and-mutes makes the cache an authority that key-name reconciliation cannot validate, since it detects a missing uid but never a stale token or stale mute. So there is no push cache. One index survives, in a shape that cannot lose updates:

**`slatefx:<fixtureId>:<leagueCode>` → `{ "period": "<period>" }`** — one key per pair, written only by that league's own publish path, so concurrent publishes touch disjoint keys. Discovery is `KV.list` returning league codes **in the key names**, zero value reads. Contents are league codes and a period: no user data, no tokens, no mutes. It is a discovery hint, never an authority — the consumer re-reads the real slate, so a stale entry costs a wasted job and never a wrong send.

**Read rule, adopted verbatim:** *No unbounded member × fixture fan-out in the cron invocation. Bounded authoritative reads inside capped Queue jobs are allowed and required for the pre-send privacy/correctness check.*

**Flow.** Cron plans and never sends: due fixtures inside the preserved 60-minute window, a DO planner lease per fixture, league codes from `slatefx:` key names, membership from `member:` key names, league chosen as the lexicographically smallest eligible code. Jobs of **≤45 triples over ≤3 fixtures and ≤3 leagues**, `max_batch_size = 1`, so a consumer batch can never exceed 45 APNs requests. Two planning passes per fixture — the initial plan and one sweep that asks the DO who is still unsent.

Consumer does the authoritative pre-send check — `push:<uid>` (token, mute), `member:<code>:<uid>`, `picks:<fixtureId>`, `custom_slate:` — then sends with `apns-expiration` = kick-off and a stable `apns-collapse-id` per user+fixture, acks successes, retries failures via Queue semantics. Payload carries `po: { v, f, l }` privately; lock-screen copy says **"Your league"**, never a user-created name; old clients ignore `po` (X1, N4).

## 4. The claim/retry state machine (correction A)

Sol found a real contradiction. `INSERT … ON CONFLICT DO NOTHING` returns only newly-inserted rows, so a row left `claimed` by a crash could **never** be reclaimed — which made the retry trace built on top of it false. The design is corrected to an explicit bounded lease.

**States:** `claimed` (leased, bounded by `claim_until`) · `sent` (terminal) · `failed` (transient, reclaimable at once) · `dropped` (terminal give-up).

```sql
INSERT INTO delivery (uid, fixture_id, league, state, claim_until, attempts, kickoff_at)
VALUES (:uid, :fx, :league, 'claimed', MIN(:now + :lease, :kickoff), 1, :kickoff)
ON CONFLICT (uid, fixture_id) DO UPDATE SET
    state       = 'claimed',
    claim_until = MIN(:now + :lease, delivery.kickoff_at),
    attempts    = delivery.attempts + 1,
    league      = excluded.league
  WHERE (delivery.state = 'failed'
      OR (delivery.state = 'claimed' AND delivery.claim_until <= :now))
    AND delivery.attempts < :maxAttempts
    AND :now < delivery.kickoff_at
RETURNING uid, fixture_id, league, attempts;
```

The conflict clause decides all six outcomes, so they hold under concurrency without an enclosing transaction:

| Existing row | Outcome |
|---|---|
| absent | inserted and leased — **returned** |
| `sent` | matches nothing — **never returned**, terminal |
| `dropped` | matches nothing — **never returned**, terminal |
| `claimed`, lease live | `WHERE` fails — **not returned**, cannot be stolen |
| `claimed`, lease expired | re-leased, `attempts + 1` — **returned** |
| `failed` | re-leased immediately — **returned**, no wait for the lease |

`LEASE_MS = 120,000` — roughly 80× the worst observed job and far inside the 60-minute window — and **clamped to kick-off**, so a lease can never outlive the window its reminder is allowed to be delivered in. `MAX_ATTEMPTS = 5` covers four queue deliveries plus one lease-expiry reclaim.

**The crash window remains, and remains documented.** A consumer that dies after APNs accepts but before `sent` is recorded leaves a `claimed` row; once the lease expires the work is reclaimable and the user may receive a second push. `apns-collapse-id` per user+fixture makes Apple replace rather than stack it, so the lock screen still shows one notification. At-least-once with collapse, never at-most-once.

### 4.1 Executed traces

The SQL above is not prose: it lives in `docs/design/notify-ledger.spec.mjs` and is executed against real SQLite (`node:sqlite`) by `test/ledger.test.mjs`. **13 traces, all passing:**

| Trace | Asserted |
|---|---|
| First claim | granted, leased to `now + 120s` |
| **Concurrency** | a second consumer 1s later gets nothing; the refused claim burns no attempt |
| **Lease expiry** | refused at `lease − 1ms`, granted at `lease`, `attempts` becomes 2 |
| **Explicit failure** | `failed` is reclaimable at once, without waiting out the lease |
| **`sent` is terminal** | no reclaim at +600ms, past the lease, or up to kick-off |
| **Partial retry** | of `u1` sent / `u2`,`u3` failed, redelivery returns exactly `u2`,`u3` |
| **Crash after APNs** | no reclaim while leased; reclaimable after expiry — the documented window |
| **Attempts capped** | exactly 5 grants over 8 attempts; a poisoned triple cannot cycle |
| Lease vs kick-off | a 120s lease on a fixture 30s out is clamped to kick-off |
| Past kick-off | nothing claimed at or after kick-off |
| `dropped` terminal | never reclaimed |
| Prune sweep | removes past fixtures only |
| Overlapping leagues | one claim across three leagues; the chosen league is not overwritten |

## 5. Retry-aware queue budget (correction B)

`max_retries = 3` (up to four deliveries), `dead_letter_queue` attached as a diagnostic sink with **no consumer** — DLQ messages expire at the 24-hour retention rather than being read.

| Message outcome | Queue operations |
|---|---:|
| First attempt succeeds | write 1 + read 1 + delete 1 = **3** |
| Max retry, then succeeds | write 1 + read 4 + delete 1 = **6** |
| Max retry, then DLQ | write 1 + read 4 + delete 1 + DLQ write 1 = **7** |

Every budget below is sized at **7**, the ceiling.

**No uncontrolled retry loop.** Throwing is what schedules a redelivery, and a redelivery spends more budget — so **on budget exhaustion the consumer acks and records a drop; it never throws.** Two independent caps make a loop impossible: the queue's own `max_retries`, and `MAX_ATTEMPTS` in the ledger, which stops reclaiming a triple regardless of how often the queue presents it.

Because a redelivered message re-claims before it re-reads, a retry only re-reads the **still-unsent remainder**, not the original 45. A job that failed on three sends re-reads three. The ceiling below assumes the pathological case where every job fails wholesale every time.

## 6. Daily and rolling-31-day budgets (correction C)

Paid allowances are monthly, so daily caps alone cannot guarantee zero incremental charge. Every daily cap is therefore set at **monthly cap ÷ 31**, which makes it arithmetically impossible for the daily guard to breach the monthly one.

Counters live in the Durable Object as one row per UTC day and one per rolling window, and **the check rides on the DO call the planner and consumer already make**, so guarding costs no additional requests.

### 6.1 Behaviour when a budget is exhausted

1. **Stop creating work.** The cron checks both the daily and rolling-31-day counters before planning. At or over either, it plans nothing further: no new messages, no new claims.
2. **Spill only within the permitted reminder window.** Already-enqueued work delivers *while its fixture is pre-kick-off*. The consumer drops anything started; `apns-expiration` makes Apple discard anything in flight that outlives kick-off. Nothing is re-planned.
3. **Then drop, with a diagnostic.** A bounded `dropped` row per (day, fixture) — fixture, league count, uid count, reason, timestamp — plus a log line, capped per day so the diagnostic cannot consume the storage budget.
4. **Ack, never throw.** Exhaustion acks the message so the queue stops redelivering it. This is what keeps exhaustion from becoming a retry loop that spends more.
5. **Never block settlement.** Picks, results and settlement share no queue, no Durable Object, no counter and no code path with delivery.

### 7.1 The claim, narrowed

I can guarantee **what the feature itself consumes**: every metric is capped, and every cap is a fraction of the included allowance shown above.

I cannot assert an absolute account-wide zero cost, and I am not asserting one. Three things remain outside what I can evidence:

- **The billing-cycle boundary is unknown.** The wrangler token has no billing scope, so the figures above are a rolling 31 days rather than the actual cycle. A rolling window is the conservative choice, but it is not the cycle.
- **Worker CPU is bounded, not measured** — a percentile range, not a total.
- **KV stored data and any other product on the account are not measured here.**

So the accurate claim is: **on the metrics measured above, the feature at its own caps cannot push the account past any included allowance** — worst case 64.6% of KV reads, 23.2% of queue operations, 45% of Worker CPU. Confirming the cycle boundary and stored-data position needs Adam's billing view.

## 9. Traces

| Scenario | Behaviour |
|---|---|
| **Concurrency** | Lease-guarded upsert in the single-threaded DO. One consumer claims; the other's `WHERE` fails and it sends nothing. Executed. |
| **Retry** | Redelivery re-claims; `sent` rows match nothing, `failed` and lease-expired rows return. Successes never re-sent, only the remainder retries. Executed. |
| **Lease expiry** | An abandoned claim becomes reclaimable exactly at `claim_until`, not before. Executed. |
| **Crash between send and record** | Row stays `claimed`; reclaimable after expiry; may re-send. `apns-collapse-id` makes Apple replace rather than stack. At-least-once with collapse. Executed. |
| **Poisoned triple** | `MAX_ATTEMPTS` stops reclaiming after 5 grants regardless of queue behaviour. Executed. |
| **Budget exhausted mid-window** | Planning stops; enqueued work delivers only while pre-kick-off; the remainder is acked and dropped with a diagnostic. No retry loop, no charge, no settlement impact. |
| **Overlapping cron** | DO planner lease per fixture; the second run plans nothing. Even without it, the claim dedupes at send time. |
| **Stale index** | Consumer re-reads the authoritative slate and drops the triple. Wasted job, no wrong send. One writer per key, so a missing key cannot arise from contention. |
| **Queue unavailable** | `sendBatch` throws in the cron, caught and logged; nothing enqueued; the next tick retries in-window. Degrades to silence. |
| **DO unavailable** | The claim throws; the consumer does not ack; the queue redelivers. Fail-closed — no claim, no send. Degrades to silence, never duplicates. |
| **User in 3 overlapping leagues** | One claim; the primary key `(uid, fixture_id)` makes a second unclaimable and the chosen league is not overwritten. Executed. |
| **Pick saved between plan and send** | The consumer's authoritative `picks:` read excludes them before any APNs call (N2). |

## 10. Capacity

**10,000 recipients is formally unsupported**, as instructed. The binding constraint is the 15,000/day sends budget:

| Pick behaviour | Sends / user / day | Supported recipients |
|---|---:|---:|
| Absolute worst shape (nobody ever picks) | 10 | **1,500** |
| Realistic (most picks saved before the window) | 3 | ~5,000 |

The required 1,000-recipient scale is supported at absolute worst shape with 50% margin. Beyond that, reminders stop being created and §6.1 applies.

## 11. The N5 claim

| Fan-out class | Reads in the cron invocation |
|---|---|
| per recipient | **0** — no push cache exists; the `push:` read happens inside a capped job, which the revised rule requires |
| per recipient × fixture | **0** — pick state is one read per fixture, delivery state is a DO claim |
| per member | **0** — membership from `member:` key names |
| per league | **0** — slate membership from `slatefx:` key names |

Asserted, not eyeballed: the harness counts every `KV.get`/`put`/`list`, DO call, queue operation and `sendPush` at both scales, and fails if any total exceeds §3, if any per-recipient read appears in the cron, or if any daily or rolling-31-day budget in §6 is breached.
