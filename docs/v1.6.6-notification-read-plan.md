## 1. Plan, envelope and the one runtime dependency

**The plan authority is Adam, the account holder: Workers Paid, knowingly enabled.** That supersedes the zero-hard-cost ruling for the existing Workers baseline only. No additional paid services and no incremental usage charges are authorised.

The account's usage evidence records **observed operating limits**, not a billing plan: KV reads sustained above the documented Free daily caps on 18 of the last 31 days with zero errors. It is not offered as proof of the plan. Its significance is operational:

> Free-tier quotas are not enforced as hard caps on this account. The design cannot rely on the platform to stop it, so it stops itself (§5).

### 1.1 Metered usage vs execution profile — these are different claims

| | Claim |
|---|---|
| **Metered usage** | The design **requires Workers Paid**, and every feature-level **Paid metered dimension** is capped below its included allowance (§5). This is the cost guarantee. |
| **Execution profile** | The design **requires the Paid runtime** and is not claimed to fit the Free execution envelope. |

Worker CPU is deliberately **excluded** from any claim about Free-tier quotas: Free CPU is a **per-invocation execution limit**, not a monthly metered allowance, so "below the Free quota" is not a meaningful statement about it. It is capped against its **Paid** included allowance like every other metered dimension.

The execution dependency is specific and worth stating rather than glossing: a consumer invocation performs up to 45 APNs fetches and ~96 bounded KV reads. Its external subrequests (≤45) fit Free's limit of 50 and its internal operations (~98) fit Free's 1,000 — but its **CPU time does not plausibly fit Free's 10 ms per invocation**. The confirmed Paid baseline is therefore an **explicit runtime dependency of this design**, while all feature-level metered usage remains hard-capped below included allowances.

## 2. Architecture

**Queues + one SQLite Durable Object**, ratified in principle. Fan-out was withdrawn: Cloudflare documents *"a maximum of 32 Worker invocations"* per request and the earlier design needed ~75. A second reason is independent of plan — **the 6-simultaneous-connection limit is identical on Free and Paid**, so no single invocation can push thousands of notifications however large its subrequest ceiling.

**Cron plans and never sends.** Due fixtures inside the preserved 60-minute window; a DO planner lease per fixture; league codes from `slatefx:` key names; membership from `member:` key names; league chosen as the lexicographically smallest eligible code. Jobs of **≤45 triples over ≤3 fixtures**. Leagues per job are deliberately unbounded — see §5.1.

**Consumer does the authoritative pre-send check** — `push:<uid>` (token, mute), `member:<code>:<uid>`, `picks:<fixtureId>`, `custom_slate:` — reserves APNs budget (§4), sends with `apns-expiration` = kick-off and a stable `apns-collapse-id` per user+fixture, then records the outcome under its fencing token.

**Index.** `slatefx:<fixtureId>:<leagueCode>` → `{ "period": "<period>" }`. One key per pair, written only by that league's own publish path, so concurrent publishes touch disjoint keys. `KV.list` returns league codes **in the key names**, zero value reads. Contents are league codes and a period: no user data, no tokens, no mutes. A discovery hint, never an authority — the consumer re-reads the real slate, so a stale entry costs a wasted job and never a wrong send. There is **no push cache**: tokens, mutes and membership are read authoritatively inside the capped job.

**Read rule, adopted verbatim:** *No unbounded member × fixture fan-out in the cron invocation. Bounded authoritative reads inside capped Queue jobs are allowed and required for the pre-send privacy/correctness check.*

**Payload.** `po: { v, f, l }` carried privately; lock-screen copy says "Your league", never a user-created name; old clients ignore `po` (X1, N4).

## 3. The claim state machine

Four states: `claimed` (leased, bounded by `claim_until`, fenced by `claim_gen`) · `sent` (terminal) · `failed` (transient, reclaimable at once) · `dropped` (terminal).

`claim_gen` is a **fencing token**: a per-row generation that strictly increases on every grant. Every mutation requires the generation it was granted with, which is what stops a consumer whose lease expired from reaching into the claim that replaced it.

```sql
INSERT INTO delivery (uid, fixture_id, league, state, claim_gen, claim_until, attempts, kickoff_at)
VALUES (:uid, :fx, :league, 'claimed', 1, MIN(:now + :lease, :kickoff), 1, :kickoff)
ON CONFLICT (uid, fixture_id) DO UPDATE SET
    state       = 'claimed',
    claim_gen   = delivery.claim_gen + 1,
    claim_until = MIN(:now + :lease, delivery.kickoff_at),
    attempts    = delivery.attempts + 1,
    league      = excluded.league
  WHERE (delivery.state = 'failed'
      OR (delivery.state = 'claimed' AND delivery.claim_until <= :now))
    AND delivery.attempts < :maxAttempts
    AND :now < delivery.kickoff_at
RETURNING uid, fixture_id, league, claim_gen, attempts;
```

`SENT`, `FAIL` and `DROP` each carry `AND state = 'claimed' AND claim_gen = :gen`.

| Existing row | Outcome of a claim |
|---|---|
| absent | inserted, generation 1 — **returned** |
| `sent` | matches nothing — **terminal** |
| `dropped` | matches nothing — **terminal** |
| `claimed`, lease live | `WHERE` fails — **cannot be stolen** |
| `claimed`, lease expired | re-leased, generation + 1 — **returned** |
| `failed` | re-leased immediately, generation + 1 — **returned** |

`LEASE_MS = 120,000` (~80× the worst observed job, far inside the 60-minute window) and **clamped to kick-off**, so a lease can never outlive the window its reminder may be delivered in. `MAX_ATTEMPTS = 5`.

**Attempts exhaustion is terminal, not ambiguous.** A sweep transitions any row at `MAX_ATTEMPTS` — `failed`, or `claimed` with an expired lease — to `dropped` with `drop_reason = 'attempts-exhausted'` and records a bounded diagnostic. It never touches a live lease.

**The crash window remains, and is documented.** A consumer that dies after APNs accepts but before `sent` is recorded leaves a `claimed` row; once the lease expires the work is reclaimable and the user may receive a second push. `apns-collapse-id` makes Apple replace rather than stack it, so the lock screen shows one notification. At-least-once with collapse, never at-most-once. The zombie cannot corrupt the new owner: its generation is stale.

### 3.1 Executed traces — 25, all passing

| Group | Traces |
|---|---|
| **Fencing** | stale owner cannot mark the new claim `sent`; cannot mark it `failed`; cannot `drop` it; the real owner still can in each case; generations strictly increase and are never reused; `dropped` cannot be revived by a stale owner |
| **Concurrency** | a second consumer 1 s into a live lease gets nothing, and the refusal burns neither an attempt nor a generation |
| **Lease expiry** | refused at `lease − 1 ms`, granted at `lease`, generation and attempts both advance |
| **Failure** | `failed` is reclaimable at once without waiting out the lease |
| **Exhaustion** | exactly 5 grants over 8 attempts; the sweep transitions to `dropped` with a diagnostic; a live lease is never swept from under its owner; the diagnostic collapses 500 uids to one counted row |
| **Retry** | of u1 sent / u2, u3 failed, redelivery returns exactly u2 and u3 |
| **Terminal** | `sent` survives any lease expiry up to kick-off; nothing is claimed at or after kick-off; a 120 s lease on a fixture 30 s out is clamped |
| **Scope** | one claim across three overlapping leagues, and the chosen league is not overwritten |
| **Prune** | past fixtures removed, future ones kept |

## 4. Queue configuration and APNs attempt budget

### 4.1 Queue

| Setting | Value |
|---|---|
| `max_batch_size` | **1** — so a consumer batch can never exceed 45 APNs requests |
| `max_retries` | **3** (up to four deliveries) |
| `dead_letter_queue` | **none** — removed |
| `max_concurrency` | **10** |
| `max_batch_timeout` | 5 s |
| `retry_delay` | **150 s** — longer than the 120 s lease, so a redelivery after a crash lands *after* the lease has expired |

The DLQ is removed. Cloudflare documents that a message retried three times and dead-lettered incurs **five read operations**, and an unconsumed Paid-plan queue retains for **four days**, whose eventual deletion is itself an operation. The strongly-consistent `dropped_log` in the ledger already records give-ups better than an unread queue would, so the DLQ was cost without a reader.

Operation accounting uses the documented ceiling **even though no DLQ is attached**, which is the conservative direction:

| Outcome | Operations |
|---|---:|
| First attempt succeeds | 1 write + 1 read + 1 delete = **3** |
| Retried to the ceiling | 1 write + **5 reads** + 1 delete = **7** |

### 4.2 A crashed lease versus a queue redelivery

A redelivery can arrive while the previous delivery's lease is still live. The consumer resolves each triple by its ledger disposition, and the message's fate follows:

| Ledger state | Disposition | Message |
|---|---|---|
| `sent` / `dropped` | terminal — nothing owed | contributes to the **ack** |
| `failed` | reclaim immediately, new generation | proceed |
| `claimed`, lease **live** | a crashed delivery still owns it | **retry** — acking here would silently lose the reminder |
| `claimed`, lease **expired** | reclaim, new generation | proceed |

`retry_delay = 150 s` exceeds `LEASE_MS = 120 s`, so the redelivery that follows a crash finds the lease already gone rather than bouncing off it. The full sequence fits the window with room: three retry gaps plus one lease is **570 s against a 3,600 s reminder window**, asserted.

**Two production sequences, executed end to end through delivery → lease → redelivery:**

- **Crash before APNs** — delivery 1 claims and dies. Delivery 2 at `retry_delay` finds the lease expired, reclaims at generation 2, sends. **Not lost**, and exactly one attempt was ever reserved.
- **Crash after APNs** — delivery 1 claims, reserves its attempt, APNs accepts, then dies before recording. Delivery 2 reclaims and re-sends. **Not lost**, at-least-once with collapse ID, and the second attempt correctly draws from the **retry** pool rather than being charged to first delivery. The zombie's stale generation cannot touch the row.

### 4.3 The budget is on APNs *attempts*, not successes

A wholesale failure attempts APNs four times, so budgeting successes would have left failures unpriced. The metric is **APNs attempts**, reserved **atomically in the Durable Object before each fetch**; failed calls consume it.

**Two pools, so a retry can never starve a first delivery.** At the product's maximum shape — a 20-fixture round with up to four deliveries — one user can absorb **eighty** attempts, more than enough for a retry storm to consume capacity that recipients planned later still need.

| Pool | Cap/day | Drawn by |
|---|---:|---|
| `apns_initial` | **20,000** | the first APNs attempt for a `(uid, fixture)` |
| `apns_retry` | **5,000** | every attempt after the first |
| **Combined ceiling** | **25,000** | — |

`apns_initial` is sized to the maximum shape at the required scale: **1,000 recipients × 20 fixtures = 20,000 first attempts.** The pool is chosen from the ledger's `apns_tried` flag on the claimed row, so it is a property of the recipient's own delivery history, not of the message that happens to carry it.

**Adversarial ordering, executed:** 9,000 retry reservations are issued *before* any first delivery. The retry pool caps at exactly 5,000, and **all 20,000 first attempts remain available afterwards**; combined spend never exceeds 25,000.

### 4.3.1 The attempt grant is one atomic fenced step

Reserving from a pool and then separately marking the row tried is two writes with a gap between them, and **a crash in that gap spends INITIAL capacity without recording that it was spent** — the redelivery then spends INITIAL again, defeating the protection the pools exist for.

So it is one transaction: verify the fence, choose the pool from `apns_tried`, reserve exactly one slot, set `apns_tried`, commit. Either all of it happened or none of it did.

**Executed:** the atomic step returns permission and pool together; a **stale generation spends nothing** and marks nothing; a **crash inside the transaction rolls back both the reservation and the mark**, so the redelivery correctly draws from INITIAL exactly once; a budget-refused grant does not mark the row tried; and 300 concurrent grants against a pool with 100 slots left grant exactly 100.

Reservation is a read-compute-write inside a single Durable Object call, and a Durable Object is single-threaded, so it is atomic with respect to every other consumer — two consumers cannot both see the same headroom and both spend it. Partial grants are deliberate: a consumer asking for 45 with 10 left gets 10 and drops the rest, rather than failing at the boundary.

**When either pool is exhausted:** no further APNs fetch occurs; the remaining work is **acknowledged and dropped** with a fenced `DROP` and a bounded diagnostic. It never throws — throwing is what buys another delivery, and that is what would turn exhaustion into a retry loop.

### 4.4 Budget ordering

The claim that a budget-dropped delivery performs no authoritative reads is only worth making if the ordering can prove it. `deliverMessage()` in the ledger specification **is** that ordering:

1. Reserve the delivery's **worst-case KV-read allowance** (45×2 + 6 = 96) **before any KV read**.
2. If it is unavailable — **acknowledge and drop, having read nothing**. See §4.4.1: the drop is made terminal in that same transaction.
3. Only then run the authoritative eligibility checks.
4. Reserve the **exact** APNs attempt from the correct pool **immediately before the fetch**.
5. A failed fetch **keeps** its reservation.
6. Unused read allowance **stays consumed**. Conservative beats optimistic.

**Executed:** a budget-dropped delivery runs the eligibility callback **zero** times; a message whose second triple is ineligible still consumes all 96 reserved reads; partial eligibility spends 15 attempts across 45 triples; a wholesale failure charges all 45 and returns *retry*; the pool boundary is honoured mid-message with the remainder dropped under its own fence; and concurrent consumers cannot exceed the KV-read pool or either APNs pool — 40 interleaved consumers spend exactly the pool and not one more.

#### 4.4.1 A read-budget refusal must be terminal, not merely reported

Reporting a triple as dropped in a return value is not dropping it. Nothing in the ledger said so, so the planner would offer it again — the message was acknowledged and the work quietly came back.

So the refusal now terminalises **inside the same transaction as the failed reservation**, which means it costs **no additional Durable Object call**:

- every **safe** triple — absent, `failed`, or `claimed` with an expired lease — becomes `dropped` with reason `kv-read-budget-exhausted`;
- `sent`, already-`dropped` and another consumer's **live fenced claim** all fail the conflict clause and are left exactly as they are;
- the bounded diagnostic records the exact count, one row per (day, fixture, reason);
- zero KV reads, zero eligibility callbacks, zero APNs calls;
- the message is acknowledged.

Row-write accounting for this path is one row per terminalised triple plus one diagnostic row per fixture — no budget row, because a refused reservation writes nothing.

**Executed:** first-delivery triples with no rows become terminally dropped; `failed` and lease-expired rows become terminally dropped; `sent`, already-dropped and live-claimed rows are untouched, including the live lease's generation and expiry; a terminally dropped triple **cannot be reclaimed at any later time in the window, nor replanned into an attempt** even once read budget frees up; the diagnostic records 30 and 15 across two fixtures exactly; a crash midway rolls back both the drops and the diagnostic, and the retry then completes cleanly; and the refusal path runs the eligibility callback and APNs zero times while consuming no read budget.

**The planner reserves before enqueueing, not after.** Once a message is on the queue its worst case is unavoidable: Cloudflare has already charged the write, and up to four deliveries with their reads and deletes follow whatever the consumer decides. The planner therefore reserves **`{ queue_ops: 7, worker_requests: 4, do_requests: 12 }`** per message **before `sendBatch`**, rather than checking a bill already run up.

`do_requests` is **four deliveries × three calls**. An earlier value of 8 argued that a budget-refused delivery costs only one call — which is an average, not a bound: all four deliveries may perform complete work. **Executed adversarially:** a message driven through four fully-working deliveries costs exactly 12 calls, and the reservation covers it with nothing to spare; a mixed run of two working and two refused deliveries costs 8 and stays inside it.

Because the reservation is booked up front and — like the read allowance — is not handed back when unused, the DO-request **cap is checked against the reservation, not against the calls actually made.**

### 4.5 Durable Object accounting

A working delivery is **three** Durable Object round trips, not two — and a message may receive four of them, so its unavoidable worst case is **12**:

1. reserve the read allowance and claim the batch;
2. the batched atomic attempt grants, after eligibility;
3. record the sent / failed / dropped outcomes, after APNs.

A delivery refused its read allowance costs one. Rows written are now named individually rather than approximated — the previous `attempts × 2 + deliveries` understated every triple that is **claimed and then dropped without an APNs attempt**, which is most of a wholesale-failure day:

| Row write | Source |
|---|---|
| claims and reclaims | one per claimed triple |
| `apns_tried` | one per granted attempt |
| sent / failed outcome | one per granted attempt |
| **dropped outcome, no attempt made** | one per claimed-then-dropped triple |
| budget rows | two per delivery — read reservation, attempt grants |
| bounded diagnostics | capped per day |

### 5.1 What the distribution costs, and the margin it leaves

A job's reads are **2 per recipient + one pick map per distinct fixture + one slate per distinct league/period**, priced from the job's own composition. The same 45 recipients cost **94 reads in one league and 136 across 45 one-person leagues.**

Leagues per job are deliberately unbounded. Capping them at three made the read cost look constant, but only for large leagues: a thousand one-person leagues hit the cap after three triples and turned 445 messages into 6,680 — more than the queue and Durable Object pools can fund, so most of a round would simply never be planned. The cap was buying a tidy constant at the price of the product working for small leagues.

**The 1.14× KV-read margin is withdrawn. The honest figure is 1.00×**, and it is the fragmented max-retry day that produces it: 109,981 of the 110,000-read pool spent, with **193 deliveries refused**. Those refusals are the designed behaviour, not a failure — they terminally drop with a bounded diagnostic — but the pool is genuinely the binding constraint at that shape and the report should not pretend otherwise.

**Every first attempt still fits, at every distribution.** The first pass costs at most 60,462 reads against a 110,000 pool; the refusals only ever fall on retries, and only after all 20,000 first attempts have been made.

### 5.2 Behaviour when a budget is exhausted

1. **Stop creating work** — the cron checks daily and rolling-31-day counters before planning.
2. **Spill only within the reminder window** — enqueued work delivers while its fixture is pre-kick-off; the consumer drops anything started, and `apns-expiration` makes Apple discard anything in flight that outlives kick-off. Nothing is re-planned.
3. **Then drop, with a bounded diagnostic** — one `dropped_log` row per (day, fixture, reason), counted rather than listed.
4. **Ack, never throw** — this is what stops exhaustion becoming a retry loop.
5. **Never block settlement** — picks, results and settlement share no queue, no Durable Object, no counter and no code path with delivery.

### 6.1 The cost claim

**What is guaranteed:** feature consumption is bounded. Every feature-level **Paid metered dimension** is hard-capped below its included allowance — the largest is 29.8%. Worker CPU is excluded from any Free-quota comparison for the reason in §1.1.

**What is not guaranteed:** absolute account-wide zero additional cost. It cannot be guaranteed from the available evidence, and is not claimed. Three things sit outside it: the **billing-cycle boundary**, **aggregate Worker CPU**, and **KV stored data or any other product** on the account.

**Required before configuration is enabled:** a final **read-only billing and headroom check**, covering the actual billing cycle, aggregate CPU and stored data, immediately before the queue and Durable Object namespace are created. That check is a precondition of the configuration step, not of this approval.

## 8. Traces

| Scenario | Behaviour |
|---|---|
| **Concurrency** | Fenced lease in the single-threaded DO. One consumer claims; the other's `WHERE` fails and it sends nothing. Executed. |
| **Stale owner** | A consumer whose lease expired cannot mark the replacement claim `sent`, `failed` or `dropped` — its generation matches nothing. Executed, all three mutations. |
| **Retry** | Redelivery re-claims; `sent` rows match nothing; only the unsent remainder returns. Executed. |
| **Crash between send and record** | Row stays `claimed`; reclaimable after expiry; may re-send. Collapse-id makes Apple replace rather than stack. At-least-once with collapse. Executed. |
| **Attempts exhausted** | Sweep transitions to `dropped` with a bounded diagnostic, never leaving an ambiguous `failed`, and never touching a live lease. Executed. |
| **Budget exhausted** | No further APNs fetch; remaining work acked and dropped with its reason; 40 interleaved consumers cannot overshoot the cap. Executed. |
| **Overlapping cron** | DO planner lease per fixture; the second run plans nothing. Even without it, the claim dedupes at send time. |
| **Stale index** | Consumer re-reads the authoritative slate and drops the triple. Wasted job, no wrong send. One writer per key, so a missing key cannot arise from contention. |
| **Queue unavailable** | `sendBatch` throws in the cron, caught and logged; nothing enqueued; the next tick retries in-window. Degrades to silence. |
| **DO unavailable** | The claim throws; the consumer does not ack; the queue redelivers. Fail-closed — no claim, no send. Degrades to silence, never duplicates. |
| **User in 3 overlapping leagues** | One claim; the primary key makes a second unclaimable and the chosen league is not overwritten. Executed. |
| **Pick saved between plan and send** | The consumer's authoritative `picks:` read excludes them before any APNs call (N2). |

## 9. Capacity

Everything below is at the product's maximum shape: **a 20-fixture published round**, which the frozen authority requires as the executed worst case and league rules permit.

| Recipients | First attempts needed | INITIAL pool | Position |
|---:|---:|---:|---|
| 100 | 2,000 | 20,000 | **Supported**, 10× headroom |

Per-user arithmetic at the maximum shape, since this is where the earlier error was:

| Basis | Attempts per user | Recipients covered |
|---|---:|---:|
| One attempt each across 20 fixtures, INITIAL pool | 20 | **1,000** |
| All four deliveries across 20 fixtures, combined cap | **80** | 312 |

**At 1,000 recipients the INITIAL pool is exactly consumed** — 1,000 × 20 = 20,000. The required scale is covered for first delivery with **no margin**. Growth beyond it would begin refusing *first* attempts rather than merely retries, so `apns_initial` is the number to raise, and it is configuration. In wholesale failure 55,000 of the 60,000 wanted retries are refused — dropped with a diagnostic while still pre-kick-off, and **first delivery is never traded for them.**

### 9.1 The maximum production sequence, executed

Run end to end through 445 queue messages at 1,000 recipients × 20 fixtures:

| Sequence | Result |
|---|---|
| First delivery at maximum shape | **all 20,000 first attempts granted**, 20,000 sent, none dropped, INITIAL exactly consumed, RETRY untouched |
| Retries arriving before later first deliveries | retry pool caps at 5,000; **all 20,000 first attempts still granted afterwards** |
| Wholesale APNs failure | first pass spends INITIAL exactly; redelivery draws only RETRY, stops at its cap, drops the remainder; KV pool never exceeded |
| Crash between claim and APNs permission | nothing charged before permission; redelivery sends, drawing INITIAL exactly once |
| Crash after permission, before fetch | attempt stays spent; redelivery sends and is charged to **RETRY**, not to first delivery |
| Stale consumer | three stale generations spend nothing from either pool |
| Cap prevents work | remainder acknowledged, every row terminally `dropped` with `budget-exhausted`, counted in one bounded diagnostic row |

## 10. The N5 claim

| Fan-out class | Value reads in the cron invocation | How |
|---|---|---|
| per recipient | **0** | no push cache exists; the `push:` read happens inside a capped job, which the revised rule requires |
| per recipient × fixture | **0** | pick state is one read per fixture; delivery state is a Durable Object claim |
| per member | **0** | membership comes from `member:` **key names** |
| per league | **0** | the period is written into the index key's **list metadata**, so `KV.list` returns it — there is no `slatefx:` value read per league |
| per league (list calls) | **0** | membership is ONE bounded `member:` scan for the whole window, not one list per league |

The last two rows are the ones that were previously claimed rather than achieved. An earlier revision read the index value once per league to recover the period and listed `member:` once per league — at a thousand one-person leagues that is 20,000 value reads and 1,000 list calls. Both are now structural zeroes, and §10.1 counts them.

### 10.1 Counted at every distribution

The same 1,000 recipients and 20 fixtures, arranged five ways. If any per-league cost survived, these would not agree:

| Distribution | Planner value reads | Queue messages |
|---|---:|---:|
| one league | 20 | 445 |
| three leagues | 20 | 445 |
| 100 leagues | 20 | 445 |
| **1,000 one-person leagues** | **20** | **445** |
| overlapping (10 leagues, 3 each) | 20 | 445 |

**A full day** at the most fragmented shape — four cron ticks across the window, of which the planning lease makes two no-ops — costs **40 value reads, 42 list calls and 27 ledger RPCs.** Two passes × 20 fixtures = 40 pick maps, and nothing per league or per recipient anywhere.

### 10.2 Planner operations in the cost model

The planning lease is what keeps this bounded: the cron fires four times inside a one-hour window, and without it each tick would re-plan every due fixture — four times the messages for the same reminders. A fixture is planned at most **twice** a day: the initial pass, and one sweep carrying only those the ledger says are still unsent.

Per worst-shape day the planner therefore adds **40 KV value reads, ~42 list calls and ~27 ledger RPCs** to the tables in §5 — under 0.1% of every cap, which is why the margins there are unchanged.

Asserted, not eyeballed: the harness counts every `KV.get`/`put`/`list`, DO call, queue operation and APNs attempt at both scales, and fails if any total exceeds §5, if any per-recipient read appears in the cron, or if any daily or rolling-31-day cap is breached.

### 11.1 Preconditions — both must pass before the bindings are enabled

**(a) The read-only billing and headroom check** of §6.1 — actual cycle, aggregate CPU, stored data.

**(b) The slate-index ship gate.** `slatefx:` keys are written by the publish and amend paths, so **every slate published before this code exists has no index entry at all**. Those leagues would receive no reminders the moment the bindings were enabled — silently, because an empty index looks exactly like a league with nothing due. `publishSlate()` cannot repair them: it returns early on an already-published slate, which is precisely the case needing repair.

So the index is reconciled once, deliberately, and proved:

```
POST /admin/slate-index  { "secret": "...", "action": "verify" }   # read-only
POST /admin/slate-index  { "secret": "...", "action": "repair" }   # writes, then re-verifies
```

Two directions, because they catch different failures — **forward** (every published slate fixture has an index key) catches pre-existing slates and a slate write whose index write failed; **reverse** (every index key names a fixture its league still publishes) catches amendments and deletions that left dead entries behind. Both are bounded per invocation and resumable from a cursor.

**The gate is `verify` returning `ready: true`** — the scan complete in both directions, `missing: 0` and `stale: 0`. Anything else means some league gets silence or the planner keeps offering fixtures nobody is being asked to predict. A rerun of a healthy index writes nothing, which is the only evidence the repair actually finished.

**Not run.** The module is built and tested; it is invoked once, manually, behind the migration secret, and a test asserts neither the cron nor the planner calls it.
