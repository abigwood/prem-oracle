## 1. Plan, envelope and the one runtime dependency

**The plan authority is Adam, the account holder: Workers Paid, knowingly enabled.** That supersedes the zero-hard-cost ruling for the existing Workers baseline only. No additional paid services and no incremental usage charges are authorised.

The account's usage evidence records **observed operating limits**, not a billing plan: KV reads sustained above the documented Free daily caps on 18 of the last 31 days with zero errors. It is not offered as proof of the plan. Its significance is operational:

> Free-tier quotas are not enforced as hard caps on this account. The design cannot rely on the platform to stop it, so it stops itself (§5).

### 1.1 Metered usage vs execution profile — these are different claims

| | Claim |
|---|---|
| **Metered usage** | Every feature metric is hard-capped **below documented Free-tier quota levels** (§5). This is the cost guarantee. |
| **Execution profile** | The design **requires the Paid runtime** and is not claimed to fit the Free execution envelope. |

The execution dependency is specific and worth stating rather than glossing: a consumer invocation performs up to 45 APNs fetches and ~96 bounded KV reads. Its external subrequests (≤45) fit Free's limit of 50 and its internal operations (~98) fit Free's 1,000 — but its **CPU time does not plausibly fit Free's 10 ms per invocation**. The confirmed Paid baseline is therefore an **explicit runtime dependency of this design**, while all feature-level metered usage remains hard-capped below included allowances.

## 2. Architecture

**Queues + one SQLite Durable Object**, ratified in principle. Fan-out was withdrawn: Cloudflare documents *"a maximum of 32 Worker invocations"* per request and the earlier design needed ~75. A second reason is independent of plan — **the 6-simultaneous-connection limit is identical on Free and Paid**, so no single invocation can push thousands of notifications however large its subrequest ceiling.

**Cron plans and never sends.** Due fixtures inside the preserved 60-minute window; a DO planner lease per fixture; league codes from `slatefx:` key names; membership from `member:` key names; league chosen as the lexicographically smallest eligible code. Jobs of **≤45 triples over ≤3 fixtures and ≤3 leagues**.

**Consumer does the authoritative pre-send check** — `push:<uid>` (token, mute), `member:<code>:<uid>`, `picks:<fixtureId>`, `custom_slate:` — reserves APNs budget (§4), sends with `apns-expiration` = kick-off and a stable `apns-collapse-id` per user+fixture, then records the outcome under its fencing token.

**Index.** `slatefx:<fixtureId>:<leagueCode>` → `{ "period": "<period>" }`. One key per pair, written only by that league's own publish path, so concurrent publishes touch disjoint keys. `KV.list` returns league codes **in the key names**, zero value reads. Contents are league codes and a period: no user data, no tokens, no mutes. A discovery hint, never an authority — the consumer re-reads the real slate, so a stale entry costs a wasted job and never a wrong send. There is **no push cache**: tokens, mutes and membership are read authoritatively inside the capped job.

**Read rule, adopted verbatim:** *No unbounded member × fixture fan-out in the cron invocation. Bounded authoritative reads inside capped Queue jobs are allowed and required for the pre-send privacy/correctness check.*

**Payload.** `po: { v, f, l }` carried privately; lock-screen copy says "Your league", never a user-created name; old clients ignore `po` (X1, N4).

## 3. The claim state machine

Four states: `claimed` (leased, bounded by `claim_until`, fenced by `claim_gen`) · `sent` (terminal) · `failed` (transient, reclaimable at once) · `dropped` (terminal).

`claim_gen` is a **fencing token**: a per-row generation that strictly increases on every grant. Every mutation requires the generation it was granted with, which is what stops a consumer whose lease expired from reaching into the claim that replaced it.

```sql
INSERT INTO delivery (uid, fixture_id, league, state, claim_gen, claim_until, attempts, kickoff_at)
VALUES (:uid, :fx, :league, 'claimed', 1, MIN(:now + :lease, :kickoff), 1, :kickoff)
ON CONFLICT (uid, fixture_id) DO UPDATE SET
    state       = 'claimed',
    claim_gen   = delivery.claim_gen + 1,
    claim_until = MIN(:now + :lease, delivery.kickoff_at),
    attempts    = delivery.attempts + 1,
    league      = excluded.league
  WHERE (delivery.state = 'failed'
      OR (delivery.state = 'claimed' AND delivery.claim_until <= :now))
    AND delivery.attempts < :maxAttempts
    AND :now < delivery.kickoff_at
RETURNING uid, fixture_id, league, claim_gen, attempts;
```

`SENT`, `FAIL` and `DROP` each carry `AND state = 'claimed' AND claim_gen = :gen`.

| Existing row | Outcome of a claim |
|---|---|
| absent | inserted, generation 1 — **returned** |
| `sent` | matches nothing — **terminal** |
| `dropped` | matches nothing — **terminal** |
| `claimed`, lease live | `WHERE` fails — **cannot be stolen** |
| `claimed`, lease expired | re-leased, generation + 1 — **returned** |
| `failed` | re-leased immediately, generation + 1 — **returned** |

`LEASE_MS = 120,000` (~80× the worst observed job, far inside the 60-minute window) and **clamped to kick-off**, so a lease can never outlive the window its reminder may be delivered in. `MAX_ATTEMPTS = 5`.

**Attempts exhaustion is terminal, not ambiguous.** A sweep transitions any row at `MAX_ATTEMPTS` — `failed`, or `claimed` with an expired lease — to `dropped` with `drop_reason = 'attempts-exhausted'` and records a bounded diagnostic. It never touches a live lease.

**The crash window remains, and is documented.** A consumer that dies after APNs accepts but before `sent` is recorded leaves a `claimed` row; once the lease expires the work is reclaimable and the user may receive a second push. `apns-collapse-id` makes Apple replace rather than stack it, so the lock screen shows one notification. At-least-once with collapse, never at-most-once. The zombie cannot corrupt the new owner: its generation is stale.

### 3.1 Executed traces — 25, all passing

| Group | Traces |
|---|---|
| **Fencing** | stale owner cannot mark the new claim `sent`; cannot mark it `failed`; cannot `drop` it; the real owner still can in each case; generations strictly increase and are never reused; `dropped` cannot be revived by a stale owner |
| **Concurrency** | a second consumer 1 s into a live lease gets nothing, and the refusal burns neither an attempt nor a generation |
| **Lease expiry** | refused at `lease − 1 ms`, granted at `lease`, generation and attempts both advance |
| **Failure** | `failed` is reclaimable at once without waiting out the lease |
| **Exhaustion** | exactly 5 grants over 8 attempts; the sweep transitions to `dropped` with a diagnostic; a live lease is never swept from under its owner; the diagnostic collapses 500 uids to one counted row |
| **Retry** | of u1 sent / u2, u3 failed, redelivery returns exactly u2 and u3 |
| **Terminal** | `sent` survives any lease expiry up to kick-off; nothing is claimed at or after kick-off; a 120 s lease on a fixture 30 s out is clamped |
| **Scope** | one claim across three overlapping leagues, and the chosen league is not overwritten |
| **Prune** | past fixtures removed, future ones kept |

## 4. Queue configuration and APNs attempt budget

### 4.1 Queue

| Setting | Value |
|---|---|
| `max_batch_size` | **1** — so a consumer batch can never exceed 45 APNs requests |
| `max_retries` | **3** (up to four deliveries) |
| `dead_letter_queue` | **none** — removed |
| `max_concurrency` | **10** |
| `max_batch_timeout` | 5 s |

The DLQ is removed. Cloudflare documents that a message retried three times and dead-lettered incurs **five read operations**, and an unconsumed Paid-plan queue retains for **four days**, whose eventual deletion is itself an operation. The strongly-consistent `dropped_log` in the ledger already records give-ups better than an unread queue would, so the DLQ was cost without a reader.

Operation accounting uses the documented ceiling **even though no DLQ is attached**, which is the conservative direction:

| Outcome | Operations |
|---|---:|
| First attempt succeeds | 1 write + 1 read + 1 delete = **3** |
| Retried to the ceiling | 1 write + **5 reads** + 1 delete = **7** |

### 4.2 The budget is on APNs *attempts*, not successes

A wholesale failure attempts APNs four times, so budgeting successes would have left failures unpriced. The metric is **APNs attempts**, reserved **atomically in the Durable Object before each fetch**; failed calls consume it.

Reservation is a read-compute-write inside a single Durable Object call, and a Durable Object is single-threaded, so it is atomic with respect to every other consumer — two consumers cannot both see the same headroom and both spend it. Partial grants are deliberate: a consumer asking for 45 with 10 left gets 10 and drops the rest, rather than failing at the boundary.

**At the 15,000-attempt daily cap:** no further APNs fetch occurs; the remaining work is **acknowledged and dropped** with a fenced `DROP` and a bounded diagnostic. It never throws — throwing is what buys another delivery, and that is what would turn exhaustion into a retry loop.

**Executed:** normal day (67 jobs, 3,015 attempts, cap never approached); wholesale failure (940 deliveries, stops at exactly 15,000, some deliveries dropped); partial grant honoured at the boundary; **40 interleaved consumers spend exactly 15,000 and not one more**; per-UTC-day allowances; and exhaustion dropping remaining work with its reason recorded.

## 5. Operation table and cost guards

Worst shape: 1,000 recipients, 10 due fixtures, **nobody has saved any pick**. *Normal* = 20 delivery days with ~30% of eligible sends firing. *Max-retry* = 31 consecutive worst-shape days with every message delivered four times.

Every daily cap is **monthly ÷ 31**, so the daily guard cannot arithmetically breach the monthly one. Both are asserted by `test/budget.test.mjs`.

| Metric | Normal /mo | Worst /mo | Max-retry /mo | Cap /day | Cap /mo | Paid included /mo | Cap % incl. | Margin |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Queue operations | 4,020 | 20,739 | 48,391 | 7,500 | 232,500 | 1,000,000 | 23.3% | 4.80× |
| DO requests | 3,080 | 14,446 | 55,924 | 7,500 | 232,500 | 1,000,000 | 23.3% | 4.16× |
| DO rows written | 121,940 | 629,083 | 957,652 | 48,000 | 1,488,000 | 50,000,000 | 3.0% | 1.55× |
| DO rows read | 301,500 | 1,555,425 | 2,325,000 | 160,000 | 4,960,000 | 25,000,000,000 | ~0% | 2.13× |
| DO duration (GB-s) | 4 | 19 | 72 | 320 | 9,920 | 400,000 | 2.5% | 138× |
| Worker requests | 3,260 | 9,889 | 30,628 | 4,800 | 148,800 | 10,000,000 | 1.5% | 4.86× |
| Worker CPU ms | 109,400 | 217,930 | 425,320 | 58,000 | 1,798,000 | 30,000,000 | 6.0% | 4.23× |
| KV reads | 128,640 | 663,648 | 993,984 | 96,000 | 2,976,000 | 10,000,000 | 29.8% | 2.99× |
| KV writes (`slatefx:`) | 11,067 | 11,067 | 11,067 | 580 | 17,980 | 1,000,000 | 1.8% | 1.62× |
| **APNs attempts** | 60,300 | 311,085 | **465,000** | **15,000** | 465,000 | — (Apple) | — | 1.00× |

**The attempt cap is what makes the max-retry column safe.** Uncapped, a wholesale-failure day would attempt 40,140 times and drive ~90,000 KV reads. Capped, the day stops at 15,000 attempts: **223 messages, 892 deliveries, 334 of which do work, 558 acknowledged and dropped**, and 32,064 KV reads. Dropped deliveries cost a queue read and a DO call but perform no APNs fetch and no authoritative reads — which is why max-retry KV reads land at 993,984/month rather than 2.8M.

### 5.1 Behaviour when a budget is exhausted

1. **Stop creating work** — the cron checks daily and rolling-31-day counters before planning.
2. **Spill only within the reminder window** — enqueued work delivers while its fixture is pre-kick-off; the consumer drops anything started, and `apns-expiration` makes Apple discard anything in flight that outlives kick-off. Nothing is re-planned.
3. **Then drop, with a bounded diagnostic** — one `dropped_log` row per (day, fixture, reason), counted rather than listed.
4. **Ack, never throw** — this is what stops exhaustion becoming a retry loop.
5. **Never block settlement** — picks, results and settlement share no queue, no Durable Object, no counter and no code path with delivery.

**Worker CPU is not measured and is not bounded here.** The analytics API exposes percentiles only — `prem-oracle-window` p50 39 ms, p99 699 ms across 4,292 invocations in 8 days. **A p99 is not an upper bound**, and multiplying every invocation by it would not produce one either. Aggregate account CPU therefore remains unknown until actual total usage is obtained.

### 6.1 The cost claim

**What is guaranteed:** feature consumption is bounded. Every feature metric is hard-capped, every cap sits below the documented Free-tier quota level, and every cap is a small fraction of the Paid included allowance — the largest is 29.8%.

**What is not guaranteed:** absolute account-wide zero additional cost. It cannot be guaranteed from the available evidence, and is not claimed. Three things sit outside it: the **billing-cycle boundary**, **aggregate Worker CPU**, and **KV stored data or any other product** on the account.

**Required before configuration is enabled:** a final **read-only billing and headroom check**, covering the actual billing cycle, aggregate CPU and stored data, immediately before the queue and Durable Object namespace are created. That check is a precondition of the configuration step, not of this approval.

## 8. Traces

| Scenario | Behaviour |
|---|---|
| **Concurrency** | Fenced lease in the single-threaded DO. One consumer claims; the other's `WHERE` fails and it sends nothing. Executed. |
| **Stale owner** | A consumer whose lease expired cannot mark the replacement claim `sent`, `failed` or `dropped` — its generation matches nothing. Executed, all three mutations. |
| **Retry** | Redelivery re-claims; `sent` rows match nothing; only the unsent remainder returns. Executed. |
| **Crash between send and record** | Row stays `claimed`; reclaimable after expiry; may re-send. Collapse-id makes Apple replace rather than stack. At-least-once with collapse. Executed. |
| **Attempts exhausted** | Sweep transitions to `dropped` with a bounded diagnostic, never leaving an ambiguous `failed`, and never touching a live lease. Executed. |
| **Budget exhausted** | No further APNs fetch; remaining work acked and dropped with its reason; 40 interleaved consumers cannot overshoot the cap. Executed. |
| **Overlapping cron** | DO planner lease per fixture; the second run plans nothing. Even without it, the claim dedupes at send time. |
| **Stale index** | Consumer re-reads the authoritative slate and drops the triple. Wasted job, no wrong send. One writer per key, so a missing key cannot arise from contention. |
| **Queue unavailable** | `sendBatch` throws in the cron, caught and logged; nothing enqueued; the next tick retries in-window. Degrades to silence. |
| **DO unavailable** | The claim throws; the consumer does not ack; the queue redelivers. Fail-closed — no claim, no send. Degrades to silence, never duplicates. |
| **User in 3 overlapping leagues** | One claim; the primary key makes a second unclaimable and the chosen league is not overwritten. Executed. |
| **Pick saved between plan and send** | The consumer's authoritative `picks:` read excludes them before any APNs call (N2). |

## 9. Capacity

**10,000 recipients is formally unsupported**, as instructed. The binding constraint is the 15,000 APNs attempts/day cap:

| Pick behaviour | Attempts / user / day | Supported recipients |
|---|---:|---:|
| Absolute worst shape (nobody picks, wholesale retry) | 10 | **1,500** |
| Realistic (most picks saved before the window) | 3 | ~5,000 |

The required 1,000-recipient scale is supported at absolute worst shape with 50% margin. Beyond it, reminders stop being created and §5.1 applies.

## 10. The N5 claim

| Fan-out class | Reads in the cron invocation |
|---|---|
| per recipient | **0** — no push cache exists; the `push:` read happens inside a capped job, which the revised rule requires |
| per recipient × fixture | **0** — pick state is one read per fixture, delivery state is a DO claim |
| per member | **0** — membership from `member:` key names |
| per league | **0** — slate membership from `slatefx:` key names |

Asserted, not eyeballed: the harness counts every `KV.get`/`put`/`list`, DO call, queue operation and APNs attempt at both scales, and fails if any total exceeds §5, if any per-recipient read appears in the cron, or if any daily or rolling-31-day cap is breached.
