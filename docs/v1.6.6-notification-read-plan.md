## 2. The architecture

Unchanged from v2, where three of Sol's four blockers were upheld and applied.

**Fan-out is withdrawn.** Cloudflare's documented limit — *"A single request has a maximum of 32 Worker invocations, and each call to a Service binding counts towards this limit"* — killed it; v1 needed ~75 children. A second reason survives the plan question entirely: **the 6-simultaneous-connection limit is identical on Free and Paid**, so no single invocation can push thousands of notifications however large its subrequest ceiling. Queue consumer concurrency is what parallelises delivery.

**The KV marker is withdrawn.** KV is eventually consistent, its read-modify-write loses concurrent updates, and a crash between APNs success and the marker write opens a duplicate window. A KV value cannot express a claim. A SQLite Durable Object can:

```sql
CREATE TABLE IF NOT EXISTS delivery (
  uid TEXT NOT NULL, fixture_id TEXT NOT NULL, league TEXT NOT NULL,
  state TEXT NOT NULL,                       -- 'claimed' | 'sent' | 'failed'
  claimed_at INTEGER NOT NULL, sent_at INTEGER, kickoff_at INTEGER NOT NULL,
  PRIMARY KEY (uid, fixture_id)
);
```

`claim()` is one `INSERT … ON CONFLICT DO NOTHING` returning only newly-inserted rows, inside a single-threaded object. Two consumers racing the same uid/fixture: one claims, the other sends nothing. No lost updates by construction.

**The push index is deleted.** Sol's dilemma was exact — uids-only recreates per-user fan-out; tokens-and-mutes makes the cache an authority that key-name reconciliation cannot validate, since it detects a missing uid but never a stale token or stale mute. So there is no push cache. One index survives, in a shape that cannot lose updates:

**`slatefx:<fixtureId>:<leagueCode>` → `{ "period": "<period>" }`** — one key per pair, written only by that league's own publish path, so concurrent publishes touch disjoint keys. Discovery is `KV.list` returning league codes **in the key names**, zero value reads. Contents are league codes and a period: no user data, no tokens, no mutes. It is a discovery hint, never an authority — the consumer re-reads the real slate, so a stale entry costs a wasted job and never a wrong send.

**Read rule, adopted verbatim:** *No unbounded member × fixture fan-out in the cron invocation. Bounded authoritative reads inside capped Queue jobs are allowed and required for the pre-send privacy/correctness check.*

**Flow.** Cron plans and never sends: due fixtures inside the preserved 60-minute window, a DO planner lease per fixture, league codes from `slatefx:` key names, membership from `member:` key names, league chosen as the lexicographically smallest eligible code. Jobs of **≤45 triples over ≤3 fixtures and ≤3 leagues**, `max_batch_size = 1`, so a consumer batch can never exceed 45 APNs requests. Two planning passes per fixture — the initial plan and one sweep that asks the DO who is still unsent.

Consumer does the authoritative pre-send check — `push:<uid>` (token, mute), `member:<code>:<uid>`, `picks:<fixtureId>`, `custom_slate:` — then sends with `apns-expiration` = kick-off and a stable `apns-collapse-id` per user+fixture, acks successes, retries failures via Queue semantics. Payload carries `po: { v, f, l }` privately; lock-screen copy says **"Your league"**, never a user-created name; old clients ignore `po` (X1, N4).

## 3. Operation table — 100 and 1,000 recipients

Worst shape: **10 due fixtures, nobody has saved any pick**, every recipient eligible for every fixture. Users in multiple overlapping leagues are deduplicated to one notification per fixture by the DO primary key `(uid, fixture_id)` before any send.

| | **100 recipients** | **1,000 recipients** |
|---|---:|---:|
| Leagues / memberships | 25 / 150 | 250 / 1,500 |
| **Notification sends** | **1,000** | **10,000** |
| Queue messages (plan + sweep) | 24 | 235 |
| Max message size | 2.7 KB | 2.7 KB |
| **Queue operations** (write + read + delete) | **72** | **705** |
| Consumer invocations | 24 | 235 |
| APNs fetches per invocation | ≤45 | ≤45 |
| **DO requests** | **~70** | **~490** |
| DO rows written | 2,000 | 20,000 |
| DO rows read | ~5,000 | ~50,000 |
| DO storage (pruned at kick-off) | ~80 KB | ~800 KB |
| **KV reads** (notification path) | ~2,300 | ~22,600 |
| KV writes (`slatefx:` on publish) | ~36 | ~357 |
| KV list operations | ~20 | ~20 |

Per-invocation ceilings hold with room at both scales: ≤45 external subrequests against a Free cap of 50, and ~98 internal operations against a Free cap of 1,000.

**One honest exception, unchanged and unresolved by the plan ruling.** The notification path's ~22,600 KV reads/day at 1,000 recipients fits its own budget (§4), but the *existing app* already runs 70,000–577,000 KV reads/day, which is outside a Free-sized envelope on its own and is not something this release changes. The lever that would halve the notification path's reads is folding membership into `push:<uid>` — which reintroduces exactly the cached-authority problem blocker 4 correctly rejected. I do not recommend it.

## 4. Application-level daily budgets

Because Free quotas will not be enforced as hard caps here, the design enforces its own. Counters live in the Durable Object — the only strongly-consistent place available — as one row per UTC day per metric, and **the budget check rides on the DO call the planner and consumer already make**, so budgeting costs no additional requests.

**Sends is the master budget. Every other value is a backstop derived from it**, which is why they cannot contradict each other:

| Budget | Daily cap | 1,000-recipient worst day | Free quota | Margin over worst day | % of Free quota |
|---|---:|---:|---:|---:|---:|
| **Notification sends** | **15,000** | 10,000 | — | 1.5× | — |
| Queue operations | 8,000 | 705 | 10,000 | 11.3× | 80% |
| DO requests | 50,000 | ~490 | 100,000 | 102× | 50% |
| DO rows written | 40,000 | 20,000 | 100,000 | 2.0× | 40% |
| DO storage | 64 MB | ~0.8 MB | 5 GB | 80× | 1.3% |
| KV reads (notification path) | 40,000 | ~22,600 | 100,000 | 1.8× | 40% |
| KV writes (`slatefx:`) | 600 | ~357 | 1,000 | 1.7× | 60% |

Consistency check at the master cap: 15,000 sends ⇒ 334 jobs ⇒ 1,002 queue operations, ~688 DO requests, 30,000 rows written, ~32,064 KV reads. **Every one lands inside its own backstop**, so the sends cap is genuinely the first thing to bind and the others cannot be reached without it being hit first.

Every value is configuration, not a constant, so Sol can move any of them without a code change.

### 4.1 Behaviour when a budget is exhausted

1. **Stop creating work.** The cron checks budgets before planning. At or over any cap it plans nothing further that UTC day: no new queue messages, no new claims.
2. **Spill only within the permitted reminder window.** Work already enqueued may still deliver *while its fixture is pre-kick-off*. The consumer drops any triple whose fixture has started, and `apns-expiration` makes Apple discard anything in flight that outlives kick-off. Nothing is re-planned.
3. **Then drop, with a diagnostic record.** A bounded `dropped` row per (day, fixture) — fixture, league count, uid count, reason, timestamp — plus a log line. The diagnostic is capped per day so it cannot itself consume the storage budget.
4. **Never an unexpected charge.** Every cap sits below the corresponding documented Free quota and roughly two orders of magnitude below the Paid included allowance, so exhaustion produces silence, never spend.
5. **Never block settlement.** Picks, results and settlement share no queue, no Durable Object, no counter and no code path with delivery. The budget guard exists only on the notification path; a fully exhausted budget degrades reminders to silence and touches nothing else.

## 5. Capacity

**10,000 recipients is formally unsupported**, as instructed.

The binding constraint is now policy rather than platform — the 15,000/day sends budget:

| Pick behaviour | Sends per user per day | Supported recipients |
|---|---:|---:|
| Absolute worst shape (nobody ever picks) | 10 | **1,500** |
| Realistic (most picks saved before the window) | 3 | ~5,000 |

The required 1,000-recipient scale is supported at absolute worst shape with 50% margin. Beyond that, reminders stop being created and the behaviour in §4.1 applies. Raising the cap is a configuration decision for Sol, bounded by the platform envelope in §3.

## 6. Traces

| Scenario | Behaviour |
|---|---|
| **Concurrency** | Two consumers claim the same uid/fixture: `ON CONFLICT DO NOTHING` in the single-threaded DO. One claims, the other sends nothing. |
| **Retry** | Queue redelivers the whole message; `claim()` returns only rows not already `sent`. Successes are never re-sent, only failures retry — the contract the KV marker could not prove. |
| **Crash between send and record** | Unavoidable, and stated. The row stays `claimed`; redelivery may re-send; `apns-collapse-id` makes Apple replace rather than stack, so the lock screen shows one notification. At-least-once with collapse, never at-most-once. |
| **Overlapping cron** | DO planner lease per fixture; the second run plans nothing. Even without it, `claim()` dedupes at send time. |
| **Stale index** | Consumer re-reads the authoritative slate, finds the fixture amended out, drops it. Wasted job, no wrong send. A missing key cannot arise from contention: one writer per key. |
| **Budget exhausted mid-window** | Planning stops; enqueued work delivers only while pre-kick-off; the remainder is dropped with a diagnostic row. No charge, no settlement impact. |
| **Queue unavailable** | `sendBatch` throws in the cron, caught and logged; nothing enqueued. The next tick retries while the fixture is still in window. Degrades to silence. |
| **DO unavailable** | `claim()` throws; the consumer does not ack; the Queue redelivers. Fail-closed by choice — no claim, no send. Degrades to silence, never to duplicates. |
| **User in 3 overlapping leagues** | One triple, lexicographically smallest league code; the DO primary key makes a second unclaimable. Exactly one notification (N1). |
| **Pick saved between plan and send** | The consumer's authoritative `picks:` read excludes them before any APNs call (N2). |

## 7. The N5 claim

| Fan-out class | Reads in the cron invocation |
|---|---|
| per recipient | **0** — no push cache exists; the `push:` read happens inside a capped job, which the revised rule requires |
| per recipient × fixture | **0** — pick state is one read per fixture, marker state is a DO claim |
| per member | **0** — membership from `member:` key names |
| per league | **0** — slate membership from `slatefx:` key names |

Asserted, not eyeballed: the harness counts every `KV.get`/`put`/`list`, DO call, queue operation and `sendPush` at both scales and fails if any total exceeds §3, if any per-recipient read appears in the cron, or if any budget in §4 is breached.
